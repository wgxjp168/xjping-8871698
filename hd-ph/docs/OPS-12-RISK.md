## 12.2 高概率风险（需重点防控）

### R01: 局域网络中断

**风险描述**: 卫生院网络故障导致前端无法访问服务器，设备无法传输数据

```
影响范围: 故障机构当日体检业务中断
可能原因:
  - 交换机/路由器硬件故障
  - ISP线路故障
  - 防火墙策略误操作

应对措施:
【预防】
  □ 关键网络节点（交换机/路由器）配置双电源
  □ 核心链路双冗余（主/备线路）
  □ 变更防火墙规则需要二人审核

【发生时应急】
  □ 立即切换备用网络（4G/5G热点临时替代）
  □ 启用离线模式（见R01-A: 轻量离线版）
  □ 手工记录数据，网络恢复后批量补录

【R01-A: 离线模式方案（二期开发）】
  在各卫生院部署轻量本地服务（Raspberry Pi）:
  - 网络中断时自动切换到本地
  - 支持体征录入、体检单创建
  - 网络恢复后自动同步到中心服务器
  - 同步冲突由系统自动解决（时间戳优先）

恢复后操作:
  □ 核查中断期间手工记录的数据
  □ 系统管理员批量导入补录
  □ 检查设备是否在中断期间积累了数据（需设备端补发）
```

### R04: 医疗设备故障

**风险描述**: 生化仪/血常规仪等关键设备故障，无法完成检验

```
影响范围: 对应检验类型无法自动采集
故障类型:
  - ASTM通讯模块故障（不影响设备检测，只影响传输）
  - 设备硬件故障（无法检测）
  - 试剂耗尽（无法检测）

应对措施:
【预防】
  □ 每台关键设备配置备用方案（至少2台同类设备）
  □ 试剂库存告警（低于10%时通知）
  □ 定期维护保养计划（季度维保合同）

【ASTM通讯故障时】
  1. 设备检测完成后打印纸质报告
  2. 检验技师手动录入系统（体检单详情→手动添加结果）
  3. 备注字段注明"手动录入，原始纸质报告存档"
  4. 联系厂家技术支持（迈瑞: 400-700-9998）

【设备停机时】
  1. 紧急协调邻近卫生院或县医院设备使用
  2. 或推迟该居民体检（标注体检单"待检验"）
  3. 通知公卫科调整本次下乡计划
  4. 设备修复后安排补检

【设备维修期间数据管理】
  device_info → 修改设备状态为"维修中"
  避免该设备的原始数据被处理（人工标注排除）
```

### R08: 人员误操作

**风险描述**: 操作人员误删居民档案、误作废体检单等

```
影响范围: 数据准确性、可能需要人工恢复

应对措施:
【预防措施】
  □ 所有删除操作二次确认弹窗
  □ 重要操作（作废体检单/删除居民）需填写原因
  □ 关键操作权限收紧（删除权限仅管理员）
  □ 定期培训，强调操作规范

【数据安全网】
  □ 逻辑删除（deleted=1），数据永不物理删除
  □ 操作日志记录所有修改（before/after值）
  □ 每日自动备份，可恢复到昨日状态

【恢复操作】
  发现误操作后:
  1. 立即联系系统管理员
  2. 查询操作日志确认误操作记录
  3. 通过SQL恢复（设置 deleted=0）
     UPDATE resident SET deleted=0 WHERE id=? AND deleted=1;
  4. 记录恢复操作日志
  5. 复查相关数据完整性
```

## 12.3 中概率风险

### R03: 数据库主机故障

```
影响范围: 全系统不可用
恢复时间目标 (RTO): < 2小时
数据恢复目标 (RPO): 最多丢失24小时数据（日增量备份）

应对措施:
【预防】
  □ RAID磁盘冗余（RAID 1/10）
  □ MySQL主从复制（一主一从）
  □ UPS不间断电源
  □ 异地备份（每日全量备份传至异地）

【发生时】
  Step1: 确认故障类型（数据库进程/硬件/磁盘）
  Step2: 若从库可用 → 切换从库为主库（5分钟内）
  Step3: 若无从库 → 从备份恢复（1-2小时）
  Step4: 恢复后验证数据完整性
  Step5: 通知用户恢复时间估计

【主从切换操作】
  # 从库提升为主库
  mysql> STOP SLAVE;
  mysql> RESET SLAVE ALL;
  # 修改 docker-compose.yml 中各服务的 DATASOURCE_URL
  # 重启所有微服务
```

### R07: 数据泄露风险

```
影响范围: 居民个人健康信息泄露（涉及《个人信息保护法》《数据安全法》）

风险点:
  1. 数据库直接暴露（公网可访问）
  2. SQL注入获取全量数据
  3. 内部人员越权导出
  4. 开发/测试环境使用真实数据
  5. 备份文件未加密

应对措施:
【技术防护】
  □ 数据库绝对不暴露公网，仅内网访问
  □ 全部参数化查询（防SQL注入）
  □ 接口返回脱敏（身份证/手机号）
  □ 批量导出操作告警（超过100条记录发送通知）
  □ 备份文件使用GPG加密
  □ 数据库账号最小权限（禁止SELECT *、禁止导出文件）

【管理防护】
  □ 开发测试环境使用脱敏数据或模拟数据
  □ 禁止将生产数据复制到个人电脑
  □ 离职人员账号当天禁用
  □ 数据传输使用HTTPS/SFTP，禁止明文传输

【事件响应（发生泄露时）】
  1. 立即隔离受影响系统（断网）
  2. 评估泄露范围（哪些数据、多少条）
  3. 72小时内向监管部门报告（《个保法》要求）
  4. 通知受影响居民
  5. 修复漏洞后审计所有访问记录
  6. 第三方安全评估后才能恢复上线
```

### R05: DR设备接收站紧张

```
影响范围: DR检查效率降低，等待时间增加
场景: 下乡高峰期大量DR申请单积压

应对措施:
  □ DR申请单分级处理（急症优先）
  □ 建立DR检查预约排班系统（V1.1功能）
  □ 统计分析DR需求高峰，提前安排加班
  □ 与县医院协调，高峰期增加技师排班
  □ 系统每日DR完成量/积压量报表供管理决策
```

## 12.4 运营持续性风险

### R09: 系统版本升级风险

```
风险: 新版本部署导致服务中断或数据不一致

应对措施:
  □ 所有版本升级在维护窗口执行（非业务时间）
  □ 升级前必须有备份（数据库+配置）
  □ 数据库变更使用 Flyway/Liquibase 管理（二期）
  □ 保留旧版本镜像，可在5分钟内回滚
  □ 升级后运行自动化测试套件验证
  □ 灰度发布（先5%，观察30分钟，再全量）
```

### R10: 关键人员依赖风险

```
风险: 系统主要运维人员离职，导致运维能力断档

应对措施:
  □ 系统文档完整（本运营体系文档）
  □ 运维操作手册覆盖所有常规操作
  □ 关键账号（数据库root、服务器）使用密码管理工具（如KeePass）
    密码由2人分别保管部分，需双人同时在场才能操作
  □ 至少培养2名本地运维人员
  □ 与建设方签订运维服务合同（保障期3年）
  □ 每半年进行运维能力演练（模拟故障处理）
```

### R12: 法规政策变化风险

```
关注法规:
  - 《个人信息保护法》修订
  - 《数据安全法》
  - 国家卫生信息标准更新（HL7/FHIR）
  - 省卫健委对接平台接口变更

应对措施:
  □ 指定专人跟踪卫生信息化政策动态
  □ 与省/市卫健信息部门保持联络
  □ 系统架构保持开放性，对接层使用适配器模式（易于更换）
  □ 年度安全等保评估
  □ 预留10%研发预算用于合规改造
```
