## 8.2 自动质控规则

### 检验结果质控

```
【生化项目质控范围】（参考CLSI标准）

项目代码  项目名称    单位     参考下限  参考上限  危急低值  危急高值
─────────────────────────────────────────────────────────────
GLU       空腹血糖   mmol/L    3.9      6.1      < 2.8    > 22.2
ALT       丙氨酸氨基  U/L      7        40       —        > 200
AST       天冬氨酸    U/L      13       35       —        > 200
CREA      肌酐       μmol/L   44       97(女)   < 20     > 884
                              53       106(男)
UREA      尿素       mmol/L   2.5      7.1      —        > 35.7
TC        总胆固醇   mmol/L   2.85     5.2      —        > 10

【危急值处理】
当检验值超出危急值范围:
1. 系统自动标记 abnormal_flag=3（危急）
2. 页面红色醒目提示（异常标记闪烁效果）
3. 触发告警通知（短信/系统消息）给主管医生
4. 医生需在系统内"确认知晓"后告警消除
```

### 体征自动质控

```
【血压异常判定】
  收缩压 ≥ 140 mmHg  或  舒张压 ≥ 90 mmHg
  → 标记"血压偏高"，建议纳入高血压随访

  收缩压 < 90 mmHg  或  舒张压 < 60 mmHg
  → 标记"血压偏低"，建议进一步检查

【BMI异常判定】
  < 18.5  → 偏瘦（标注）
  24~27.9 → 超重（标注）
  ≥ 28    → 肥胖（标注，建议生活方式干预）

【逻辑校验规则】
  收缩压 < 舒张压           → 数据错误，禁止保存
  身高 < 100 或 > 220 cm   → 警告提示，需二次确认
  体重 < 20 或 > 200 kg    → 警告提示，需二次确认
  体温 < 35.0 或 > 41.5    → 警告提示，需二次确认
  脉搏 < 30 或 > 200        → 警告提示，需二次确认
```

## 8.3 数据完整性校验

### 体检单完整性检查

```sql
-- 每日例行完整性检查 SQL（可作为监控脚本）

-- 1. 检查已完成体检单但缺少体征数据
SELECT co.id, co.order_no, co.resident_name
FROM check_order co
LEFT JOIN vital_sign vs ON co.id = vs.order_id AND vs.deleted = 0
WHERE co.status = 2  -- 已完成
  AND vs.id IS NULL
  AND co.check_date = CURDATE()
  AND co.deleted = 0;

-- 2. 检查已完成但无任何检验结果的体检单
SELECT co.id, co.order_no, co.resident_name
FROM check_order co
LEFT JOIN check_result cr ON co.id = cr.order_id AND cr.deleted = 0
WHERE co.status = 2
  AND cr.id IS NULL
  AND co.check_date = CURDATE()
  AND co.deleted = 0;

-- 3. 检查设备原始数据积压（处理超时10分钟的待处理记录）
SELECT COUNT(*) as stuck_records
FROM device_raw_data
WHERE process_status = 0
  AND create_time < DATE_SUB(NOW(), INTERVAL 10 MINUTE)
  AND deleted = 0;

-- 4. DR申请单但无报告的统计（完成7天以上）
SELECT COUNT(*) as dr_no_report
FROM dr_order
WHERE status = 2  -- 已完成
  AND finish_time < DATE_SUB(NOW(), INTERVAL 7 DAY)
  AND id NOT IN (SELECT dr_order_id FROM dr_report WHERE deleted=0)
  AND deleted = 0;
```

## 8.4 异常数据处理

### 处理流程

```
异常发现渠道:
  a. 系统自动质控告警（危急值）
  b. 医生人工审核发现
  c. 每日数据完整性检查脚本
  d. 设备原始数据比对

异常分级处理:
┌─────────────────────────────────────────────────────┐
│ 级别 │ 描述              │ 处理时限 │ 处理人        │
├─────────────────────────────────────────────────────┤
│ P1  │ 危急值/数据完全错误  │ 2小时内  │ 值班医生+管理员│
│ P2  │ 单项结果异常/缺失   │ 当日处理  │ 检验医生      │
│ P3  │ 统计汇总偏差        │ 3日内    │ 公卫专干      │
└─────────────────────────────────────────────────────┘
```

### 数据修正操作规范

```
【允许修正的情况】
  □ 设备故障导致结果偏差（设备维修记录作为依据）
  □ 转录错误（有原始报告作为依据）
  □ 身份信息录入错误（本人核实后）

【修正操作步骤】
1. 系统管理员/高级医生在"审核"模式下操作
2. 修改字段时必填"修改原因"
3. 系统记录修改前后值 + 操作人 + 时间（审计日志）
4. 重大修改（如更改检验结果）需双人操作（申请人+审核人）

【禁止操作】
  ✗ 直接DELETE数据库记录（使用逻辑删除 deleted=1）
  ✗ 修改体检单号（全局唯一，不可更改）
  ✗ 修改已上报至平台的数据（需走正式更正流程）
```

## 8.5 数据补发机制

### 上报失败自动重试

```
触发条件: upload_task.status = 失败

重试策略（指数退避）:
  第1次失败 → 5分钟后重试
  第2次失败 → 15分钟后重试
  第3次失败 → 1小时后重试
  第4次失败 → 4小时后重试
  第5次失败 → 人工介入

实现方式（待二期开发）:
  @Scheduled(cron = "0 */5 * * * ?")  // 每5分钟检查
  public void retryFailedUploads() {
      List<UploadTask> failed = uploadTaskMapper.selectRetryable();
      for (UploadTask task : failed) {
          if (task.getRetryCount() < 5) {
              // 重新上报
              doUpload(task);
          }
      }
  }
```

### 手动补发操作

```
路径: 系统管理 → 数据上报 → 失败记录列表

操作:
  □ 查看失败原因（upload_error字段）
  □ 修复原因（如网络恢复、接口密钥更新）
  □ 选择记录 → 点击"重新上报"
  □ 查看上报结果

批量补发（用于长期网络故障后恢复）:
  选择日期范围 → "全部重新上报"
  → 系统按时间顺序逐条上报，间隔500ms（避免对方接口过载）
```

## 8.6 数据审核工作流

### 检验结果审核

```
【审核角色】
  初审: 检验技师（结果录入后）
  复审: 检验医师（异常值必须复审）
  最终: 主管医师（危急值必须签字）

【审核操作】
体检详情 → 检验结果 → 点击"审核"按钮
  → 填写审核意见（如"结果正常，与临床相符"）
  → 点击"通过"或"驳回"（驳回需说明原因，触发重新检验）

【二期开发规划】
  - 电子签名（CA证书）
  - 审核时间戳不可篡改
  - 批量审核功能（同类正常结果一键审核）
```

## 8.7 数据质量月度报告

```
每月25日生成上月质量报告，包含:

1. 体检数量统计
   - 计划数 vs 完成数（完成率）
   - 按机构/类型分布

2. 数据采集质量
   - 设备自动采集率（自动采集/总体检人次）
   - 手工录入占比
   - 数据缺失率（有体检单但缺检验结果）

3. 异常数据处理
   - 质控失控次数
   - 危急值例数及处理时效
   - 数据修正记录数

4. 设备运行情况
   - 各设备在线时长
   - 各设备数据传输成功率
   - 故障次数及修复时效

5. 上报质量
   - 平台上报成功率
   - 失败记录数及已补发数
```
